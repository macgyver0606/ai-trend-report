## 2. 작성 배경과 전제

현재 저장소에는 프로젝트 개요가 작성된 `README.md`와 기존 요구사항, 기능 분해, MVP 계획 문서가 없다. 따라서 이 문서는 저장소명인 `ai-trend-report`를 근거로 아래와 같이 프로젝트 목적을 가정하여 작성한 초안이다.

> 여러 출처에 흩어진 AI 트렌드 정보를 사용자가 정한 조건에 따라 수집하고, 핵심 내용을 요약·분류하여 읽기 쉬운 리포트로 제공하는 서비스

이 가정은 팀 검토 후 확정해야 하며, 변경될 경우 관련 기능 요구사항과 MVP 범위도 함께 수정한다.

## 3. 프로젝트 개요

### 3.1 프로젝트명

AI Trend Report

### 3.2 프로젝트 목적

AI 분야의 뉴스, 기술 동향, 신규 제품 및 주요 이슈를 일일이 찾아보는 데 드는 시간을 줄이고, 사용자가 필요한 정보를 한눈에 파악할 수 있는 요약 리포트를 제공한다.

### 3.3 해결하려는 문제

- AI 관련 정보가 여러 웹사이트와 채널에 분산되어 있다.
- 빠르게 증가하는 정보를 모두 읽고 중요도를 판단하기 어렵다.
- 출처와 게시일이 불명확한 요약은 신뢰하기 어렵다.
- 수집한 정보를 주제별로 정리하고 보고서로 만드는 데 반복 작업이 필요하다.

### 3.4 기대 효과

- AI 트렌드 탐색 및 정리 시간 단축
- 핵심 이슈를 주제별로 빠르게 파악
- 원문 출처를 통한 정보 검증 가능
- 팀 회의, 학습 및 의사결정에 활용 가능한 정형화된 보고서 제공

## 4. 대상 사용자

### 4.1 주요 사용자

| 사용자 | 주요 요구 |
| --- | --- |
| AI 분야 학습자 | 최근 AI 이슈를 이해하기 쉬운 요약으로 확인하고 싶다. |
| 개발자 및 기획자 | 기술, 서비스, 정책 등 관심 주제의 변화를 빠르게 파악하고 싶다. |
| 팀 리더 및 의사결정자 | 출처가 명확한 핵심 동향을 정형화된 보고서로 검토하고 싶다. |

### 4.2 대표 사용자 시나리오

1. 사용자는 조회 기간과 관심 주제를 입력한다.
2. 시스템은 설정한 조건에 맞는 AI 트렌드 자료를 수집한다.
3. 시스템은 중복되거나 유효하지 않은 자료를 제외한다.
4. 시스템은 자료의 핵심 내용을 요약하고 주제별로 분류한다.
5. 사용자는 생성된 리포트에서 제목, 요약, 게시일 및 원문 출처를 확인한다.

## 5. 프로젝트 범위

### 5.1 MVP에 포함하는 기능

- 조회 기간과 관심 주제 입력
- 사전에 승인된 공개 출처에서 자료 수집
- 제목, 게시일, 원문 URL 등 기본 메타데이터 저장
- 유사 URL 또는 동일 제목 기준의 중복 자료 제거
- 수집 자료의 핵심 내용 요약
- 자료의 주제별 분류
- 출처가 포함된 리포트 생성 및 화면 표시
- 입력 오류, 수집 실패, 요약 실패에 대한 기본 오류 안내

### 5.2 MVP에서 제외하는 기능

- 회원가입, 로그인 및 사용자별 권한 관리
- 결제 및 유료 구독
- 관리자 페이지
- 실시간 알림 및 정기 이메일 발송
- 사용자별 장기 관심사 학습 및 개인화 추천
- 여러 사용자가 동시에 편집하는 협업 기능
- 모바일 앱
- 고급 통계 및 예측 분석
- 완전 자동화된 사실 검증

제외 기능은 핵심 흐름이 안정적으로 동작한 이후 우선순위를 다시 검토한다.

### 6.1 요구사항 목록

| FR-011 | 결과 표시 | 사용자는 생성된 리포트를 화면에서 확인할 수 있어야 한다. | 필수 |
| FR-012 | 빈 결과 처리 | 검색 결과가 없을 경우 시스템은 빈 화면 대신 조건 변경을 안내해야 한다. | 필수 |

| FR-014 | 보고서 내보내기 | 사용자는 리포트를 파일로 내려받을 수 있어야 한다. | 선택 |
| FR-015 | 생성 이력 | 사용자는 이전에 생성한 리포트 목록을 확인할 수 있어야 한다. | 선택 |

## 8. 예외 및 오류 처리

| 상황 | 기대 동작 |
| --- | --- |
| 날짜 형식이 잘못됨 | 잘못된 입력 항목과 올바른 형식을 안내한다. |
| 종료일이 시작일보다 빠름 | 요청을 중단하고 날짜 범위 수정을 안내한다. |
| 관심 주제가 비어 있음 | 최소 한 개의 주제를 입력하도록 안내한다. |
| 외부 출처에 연결할 수 없음 | 해당 출처를 실패 처리하고 다른 출처의 수집을 계속한다. |
| 수집 결과가 없음 | 결과가 없음을 알리고 기간 또는 주제 변경을 제안한다. |
| 일부 자료의 본문을 읽을 수 없음 | 해당 자료를 제외하거나 메타데이터만 표시하고 처리 결과에 사유를 남긴다. |
| AI 요약 요청 실패 | 제한된 횟수만 재시도하고, 계속 실패하면 해당 항목을 실패 처리한다. |
| 잘못되거나 위험한 URL | 허용된 프로토콜과 승인된 출처인지 검사하고 처리 대상에서 제외한다. |

## 9. 데이터 및 외부 연동 요구사항

- 수집 대상 출처, 사용 가능한 API 및 크롤링 허용 여부를 구현 전에 확정한다.
- 각 출처의 이용 약관, 저작권 및 호출 제한을 준수한다.
- AI 요약 서비스 사용 시 모델명, 비용 한도, 요청 크기 및 재시도 정책을 환경 설정으로 관리한다.
- 원문 전체를 장기간 저장할 필요가 있는지 검토하며, MVP에서는 최소한의 메타데이터와 생성된 요약만 저장하는 방안을 우선한다.
- 실제 API 키는 `.env`로 관리하고 `.env.example`에는 예시 변수명만 제공한다.

## 10. MVP 인수 기준

다음 조건을 모두 충족하면 MVP의 핵심 요구사항이 구현된 것으로 판단한다.

1. 사용자가 유효한 기간과 하나 이상의 주제를 입력할 수 있다.
2. 승인된 출처에서 조건에 맞는 자료를 한 건 이상 수집할 수 있다.
3. 중복 자료가 결과에 반복 노출되지 않는다.
4. 각 자료에 제목, 요약, 게시일, 출처명 및 원문 URL이 표시된다.
5. 결과가 주제별로 분류된 하나의 리포트로 화면에 표시된다.
6. 잘못된 날짜 범위와 빈 주제 입력에 대해 이해 가능한 오류가 표시된다.
7. 일부 외부 연동이 실패해도 성공한 자료로 결과를 제공하거나 전체 실패 사유를 안내한다.
8. 코드와 로그에 실제 API 키나 개인정보가 노출되지 않는다.

## 11. 테스트 요구사항

### 11.1 정상 흐름

- 유효한 기간과 주제를 입력했을 때 리포트가 생성되는지 확인한다.
- 여러 출처의 자료가 주제별로 분류되는지 확인한다.
- 각 항목의 원문 URL이 올바르게 연결되는지 확인한다.
- 동일 자료가 중복 수집되었을 때 한 번만 표시되는지 확인한다.

### 11.2 오류 흐름

- 시작일보다 빠른 종료일 입력
- 관심 주제 미입력
- 수집 결과 없음
- 외부 출처 연결 실패
- AI 요약 요청 실패
- 유효하지 않거나 허용되지 않은 URL 입력

각 테스트에는 입력값, 실행 절차, 기대 결과 및 실패 시 확인할 로그를 기록한다.

## 12. 제약사항 및 위험 요소

- 현재 기술 스택과 배포 환경이 확정되지 않았다.
- 데이터 출처별 API 제공 여부와 크롤링 정책이 다를 수 있다.
- 외부 AI API 사용량에 따라 비용과 응답 시간이 달라질 수 있다.
- 생성형 AI 요약에는 누락 또는 왜곡이 발생할 수 있으므로 원문 출처 제공이 필수다.
- 기사 및 문서의 저작권에 따라 저장·노출 가능한 범위가 제한될 수 있다.
- “트렌드”의 중요도 판단 기준이 아직 정해지지 않아 초기 버전은 최신성 및 주제 일치도를 중심으로 구성한다.

## 14. 미결정 사항

다음 항목은 기능 분해 및 MVP 설계 전에 팀과 확정해야 한다.

1. 최우선 대상 사용자는 누구인가?
2. 필수로 포함할 데이터 출처는 무엇인가?
3. 자료 수집 방식은 공식 API, RSS, 웹 크롤링 중 무엇을 사용할 것인가?
4. 리포트 생성 주기는 사용자 요청형, 일간, 주간 중 무엇인가?
5. 리포트 제공 형식은 웹 화면만 필요한가, PDF 또는 Markdown 다운로드도 필요한가?
6. 요약과 분류에 사용할 AI 모델 및 월간 비용 한도는 얼마인가?
7. 자료와 리포트를 저장할 것인가? 저장한다면 보관 기간은 얼마인가?
8. 트렌드 중요도를 판단하는 기준은 최신성, 언급량, 출처 신뢰도 중 무엇인가?
9. 수업 제출물 또는 평가 기준에 별도의 필수 항목이 있는가?

## 15. 변경 관리

- 미결정 사항이 확정되면 관련 요구사항 ID, MVP 범위 및 인수 기준을 함께 갱신한다.
- 기능 추가 또는 범위 변경 시 변경 이유, 영향받는 기능, 테스트 범위를 기록한다.
- 구현 단계에서는 각 기능과 테스트가 본 문서의 요구사항 ID를 참조하도록 한다.
